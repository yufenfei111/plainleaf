# 多格式文件支持 · 可行性与实现规划

> 制作于 2026-09-26（W16 发布准备收尾后）。状态：**待评审**，未排期。
> 本文回答三件事：① 改动面有多大 ② 支持哪些格式、怎么适配 ③ 怎么做、先做什么。

---

## 一、需求理解与范围界定

**我按这个理解写的**：让一条记录可以附带**任意类型的文件**（不只是图片），
并且这些文件能被正常保存、显示、打开、备份、恢复。

⚠️ 如果你的本意是下面任一种，本文的方案需要调整，请先纠正：

| 另一种可能 | 与本文方案的差异 |
|---|---|
| **导入格式更多**（把 Word / Notion / 印象笔记导进来变成记录） | 那是「导入器」问题，改的是 `lib/features/importer/`，与附件链路基本无关 |
| **跨设备传输文件**（用 WebDAV 同步附件） | 那是 W13 云备份的延伸，改的是 `cloud_backup_service`，与"支持更多格式"是两个方向 |

本文只覆盖第一种理解。**为什么要写这一段**：项目 `docs/ideas.md` 的规则要求新需求
先登记再评估，而需求描述里"传输"一词有歧义——先对齐再动工，比做完了发现方向错了便宜。

## 二、现状评估：改动面盘点

好消息是**原始设计已经留了口子**，坏消息是**这条链路从未跑通过非图片文件**。

| 层 | 现状 | 改动量 |
|---|---|---|
| **数据表** `assets` | `kind` 字段默认 `'image'`、`durationMs` 字段已存在（`tables.dart:56-78`）——建表时就为非图片媒体预留了；`sizeBytes` / `hashSha256` 通用；`width/height/exifJson` 图片专用但**可空** | 🟢 **小**：补 1–2 个可空字段 |
| **存储层** `MediaStorage` | `importFile()` 用 `p.extension(sourcePath)` 保留原扩展名（`media_storage.dart:72`），文件名是 uuid，按 `media/yyyy/mm/` 归档 —— **天然不假设图片** | 🟢 **零改动** |
| **缩略图管线** `ThumbnailPipeline` | 硬依赖 `img.decodeImage`，非图片必然抛 `FormatException('无法解码图片')`（`thumbnail_pipeline.dart:51-89`） | 🔴 **必须改**：按类型分流 |
| **DAO** `AssetsDao` | 5 个查询全部硬编码 `kind.equals('image')`（`assets_dao.dart:73,87,98,108`） | 🟡 **只加不改**：现有查询原样保留 |
| **导入入口** | 只有一处 `_picker.pickImage(source:..., imageQuality: 90)`（`editor_page.dart:203`），且 `imageQuality` 对非图片无意义 | 🔴 **必须改**：加"选择任意文件" |
| **展示层** | 4 处直接 `Image.file`：时间轴卡片（`timeline_page.dart:874`）、那年今日（`on_this_day_card.dart:177`）、相册网格（`gallery_page.dart:281`）、查看器（`photo_viewer_page.dart:637`） | 🔴 **必须改**：按类型分派 |
| **备份/恢复** | 打包 `plainleaf.sqlite` + `media/**` + `thumb/**` 整目录（`backup_service.dart:103`），不枚举文件类型 | 🟢 **零改动**（自动兼容，但需回归验证） |
| **导出** | Markdown 只列附件相对路径清单 | 🟢 **小**：清单里带上类型 |
| **依赖** | `pubspec.yaml` 里媒体相关只有 `image_picker` | 🟡 **需新增若干**（见第五节） |

### 结论：可行，且比预想便宜

- **数据层与备份层几乎免费**——`kind` 字段和整目录打包的设计让它们天然兼容；
- **改动集中在三处**：缩略图管线分流、导入入口、展示层分派；
- **风险不在"能不能做"，而在两件事**：① 新增的平台通道依赖必须真机验证（本机 `flutter test` 覆盖不到，W14 已吃过这个教训）；② 大文件的存储与性能（见第七节）。

## 三、支持哪些格式：三档分级

关键判断：**先把"兜底档"做扎实，比先做"视频播放"重要得多**。
因为兜底档成本低、覆盖面广（任何格式都不会报错），而播放器是重量级工程。

### A 档 · 一等公民（有缩略图 + 可预览/播放）

| 类型 | 格式 | 缩略图怎么来 | 打开方式 |
|---|---|---|---|
| 图片 | jpg / png / webp / gif / heic | ✅ 已有（两级管线） | 内置查看器 |
| PDF | pdf | 渲染首页 | 内置翻页 或 系统应用 |
| 音频 | mp3 / m4a / wav / flac / ogg | 提取内嵌封面，无则类型图标 | 内置播放器 |
| 视频 | mp4 / mov / mkv / webm | 抽首帧 | 内置播放器 |

### B 档 · 二等公民（**必须做**：列表显示图标 + 文件名/大小，点开交给系统）

| 类型 | 格式 |
|---|---|
| 文档 | doc / docx / xls / xlsx / ppt / pptx / txt / md / rtf |
| 压缩包 | zip / rar / 7z / tar / gz |
| 代码/配置 | json / xml / yaml / csv / 各类源码 |
| **其他任何格式** | **一律落这一档，绝不报错** |

设计要点：B 档不是"降级处理"，而是**契约**——任何文件导进来都必须能被记录、备份、恢复、
导出，哪怕我们完全不认识它。这条契约比功能清单更重要。

### C 档 · 明确不支持（也不该支持）

CAD 图纸、3D 模型、专业格式的**内联渲染**。收益极低、成本极高。
它们的文件本身仍可导入（走 B 档），只是不能预览。

## 四、技术方案：把"图片假设"换成"按类型分派"

### 4.1 类型模型

```dart
enum AssetKind { image, video, audio, pdf, document, archive, other }
```

- 表里 `kind` 是 text 字段，**无需迁移即可写入新值**（老值 `'image'` 保持不变）；
- 但建议补两个可空字段，理由见下：

| 新字段 | 为什么需要 |
|---|---|
| `mimeType` | `kind` 是粗分类，mime 决定具体用哪个处理器（如 `image/svg+xml` 与 `image/png` 待遇不同） |
| `originalName` | 现在文件名是 uuid，**非图片文件用户必须看到"作业第三章.pdf"这种原名**，否则一堆 uuid 毫无意义 |

→ 这两个字段必须走 `MigrationStep` + 迁移测试（数据红线），老数据留空、读取时回退到 uuid。

### 4.2 类型探测：别只看扩展名

```
优先级：magic bytes（文件头） > 扩展名 > 兜底 other
```

只看扩展名会被改名的文件骗到（`.pdf` 的图片、无扩展名的文件）。
纯 Dart 的文件头嗅探只需读前几十字节，成本可忽略。

### 4.3 处理管线分流

```
importFile(source)
  → 探测类型
  → 复制到 media/yyyy/mm/{uuid}.ext        （现有逻辑，不动）
  → 生成缩略图时按 kind 分流：
       image  → 现有 ThumbnailPipeline（完全不动）
       pdf    → 渲染首页
       video  → 抽首帧
       audio  → 提取封面，无则跳过
       other  → 不生成，thumbPath = null
  → 落库（kind / mime / originalName / sizeBytes / durationMs）
```

关键：**`thumbPath = null` 必须是合法状态**。
现有的 `missingThumb` 查询已经在处理 null（只是多了 `kind='image'` 过滤），
所以"没有缩略图"这件事链路上已经容得下，UI 只需准备好图标兜底。

### 4.4 展示层：一个组件收口

现在 4 处各写各的 `Image.file`，继续这么散着改一定会漂移。建议收成一个组件：

```dart
AssetThumb(asset, size)
  → 有 thumbPath 且 kind == image  → Image.file（现有行为）
  → 有其他类型的缩略图              → Image.file
  → 都没有                          → 类型图标 + 扩展名徽标
```

4 处调用点改指向它。**这一步同时消掉了一个既有的隐患**：现在 4 处重复实现，
任何显示策略调整都要改 4 遍。

### 4.5 打开方式

| 类型 | 方式 |
|---|---|
| 图片 / PDF / 音视频（若做了内置） | 内置 viewer |
| 其余一切 | `open_filex` 之类交给系统应用 |

"交给系统"是**性价比最高的一环**：一行代码，覆盖所有 B 档格式，且不用自己维护 Office 渲染。

## 六、任务分解与优先级

### P0 · 地基（**必须整体做完，缺一项就有断点**）

| # | 任务 | 复杂度 |
|---|---|---|
| 1 | `AssetKind` 枚举 + 类型探测（magic bytes + 扩展名） | 低 |
| 2 | 数据库迁移：`mimeType` / `originalName`（MigrationStep + 迁移测试） | 中 |
| 3 | 缩略图管线按 kind 分流（非图片不再抛异常） | 中 |
| 4 | 导入入口加"选择任意文件"（保留现有选图/拍照） | 中 |
| 5 | 展示层收口成 `AssetThumb`，4 处调用点改指向 | 中 |
| 6 | 附件"打开"：非内置类型交给系统 | 低 |
| 7 | 备份/恢复 + 导出的回归验证（理论免费，必须实测） | 低 |

**完成 P0 的验收标准**：任意格式的文件 → 能导入、能在时间轴看到（图标+原名+大小）、
能点开、能被 `.plbk` 备份并恢复回来、导出 Markdown 时在清单里。**这就是你要的最小完备集。**

### P1 · 体验提升（性价比高）

| # | 任务 | 为什么值得 |
|---|---|---|
| 8 | PDF 首页缩略图 | 一个库的事，但"能看到内容"和"只看到一个图标"体验差一个量级 |
| 9 | 音频封面 + 时长 | `durationMs` 字段已预留，不用白不用 |
| 10 | 时间轴筛选器加"附件类型"维度 | 附件变多之后，找得回来才算真的支持 |

### P2 · 重量级（建议单独立项评估）

| # | 任务 | 成本提示 |
|---|---|---|
| 11 | 视频内置播放器 | 平台通道 + 后台播放 + 权限，工作量可能等于整个 P0 |
| 12 | 音频内置播放器 + 后台 | 同上 |
| 13 | 图片多选导入 | 独立小特性，可选 |

### P3 · 不建议现在做

Office 文档内联预览（需商业 SDK 或 WASM 方案）、CAD/3D 渲染。

## 七、风险与红线

| 风险 | 说明 | 应对 |
|---|---|---|
| **新增平台通道依赖** | 本机 `flutter test` 覆盖不到，可能"构建成功、装上不工作" | 每个依赖都要真机走查；沿用 W14 的教训 |
| **数据红线** | 加字段必须 MigrationStep + 迁移测试；老数据 `kind='image'` 保持不变 | 强制 |
| **性能红线** | 列表滚动 60fps：非图片没有缩略图时，不能每次滚动都去读文件来判断类型 | 类型与图标由 `kind`/`mime` 直接决定，不读文件 |
| **大文件** | 用户可能导入几百 MB 的视频，把设备塞满 | 导入时提示大小；设置页展示附件占用总量；**不做硬限制**（限制会误伤） |
| **备份包膨胀** | 附件变多样后 `.plbk` 会显著变大 | 上传云备份已有校验；建议后续考虑"仅备份元数据"选项 |
| **范围蔓延** | `ideas.md` 明确规定新需求先登记再排期 | 本需求已登记，见该文件 |

## 八、需要拍板的决策点

1. **范围**：P0 单独发一版（"任何文件都能记"），还是 P0+P1 一起？
   → 建议 **P0 独立成版**：它是完备的、可发布的，且能最快验证方向是否正确。
2. **视频/音频播放**（P2）要不要排进来？
   → 建议**先不做**。它是"想不想要"层面的功能，而 P0 是"能不能用"层面的缺失。
   等 P0 上线、有真实使用反馈后再判断值不值得投。
3. **大文件上限**：接受"只提示不限制"，还是设一个可配置上限？
   → 建议只提示。这是个人工具，限制带来的误伤大于收益。
