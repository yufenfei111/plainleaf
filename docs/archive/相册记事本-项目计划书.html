01项目概述与定位

1.1 项目背景

学生与年轻用户的记录行为正在碎片化：照片在系统相册、课堂笔记在笔记 App、待办在清单工具、心情日记又在另一个日记 App，数据彼此割裂，回看时无法还原「那天到底发生了什么」。与此同时，Day One 等成熟产品订阅价格偏高（约 34.99 美元/年），而多数国产应用存在广告、强制注册、云端数据不可控等问题。

GitHub 上「本地优先（Local-First）+ 开源 + 跨平台」的记录类工具在 2025—2026 年持续升温（详见第 2 章实测数据），证明「数据自有、离线可用、开放同步」是被验证的产品方向。

1.2 产品定位（一句话）

定位：面向学生与年轻人群的「生活 + 学习」双空间多媒体记录工具 —— 以图文时间轴为骨架，融合相册、笔记、日记、待办与学习统计；本地优先、免注册可用、支持 WebDAV 自主同步与端到端加密。

1.3 项目目标

产品目标

  • 30 秒内完成一条「图文 + 标签」记录，降低记录门槛；
  • 一条时间轴串联照片、笔记、日记、待办、学习打卡；
  • 不联网可用全部核心功能，数据可一键导出不被锁定；
  • 形成可在校园内传播的「学习分享卡片」导出能力。

个人成长目标

  • 完整经历一次「需求 → 设计 → 开发 → 测试 → 发布」闭环；
  • 掌握 Flutter 跨平台开发、本地数据库、状态管理与同步；
  • 产出可写进简历 / 竞赛答辩的开源项目（对标挑战杯、软著）；
  • GitHub 开源，争取 100+ Star 的第一版作品。

1.4 非目标（第一版明确不做）

  • 不做多人实时协同编辑（CRDT 复杂度高，列入远期）；
  • 不自建服务器做账号体系（第一版无后端，同步走用户自有 WebDAV）；
  • 不做视频剪辑、AI 生图等重能力（仅预留接口）；
  • 不上架 App Store（需付费开发者账号，Android APK + Windows 先行）。

2.3 调研结论与差异化切入点

  1. 技术路线被验证：头部同类项目（Immich、AppFlowy、Moodiary）均选择 Flutter，说明 Flutter 完全胜任「图文密集 + 多媒体 + 多端」场景，且可直接参考大量开源实现。
  2. 市场存在结构性空白：纯笔记（Joplin/Obsidian）、纯相册（Immich）、纯日记（Day One/Moodiary）三者割裂，「生活流 + 学习管理」融合型、且本地优先的产品稀缺。
  3. 开放同步是差异化卖点：Joplin 靠「WebDAV + E2EE、不绑定厂商云」获得 5.6 万 Star，验证了用户对数据自主权的付费意愿级别的重视。
  4. 学生群体被忽视：学习待办、学习计时、复习卡片、学习打卡统计、可分享的学习卡片，是现有生活记录类 App 普遍缺失的模块。
差异化公式：Day One 的多媒体记录体验 + 格志的引导模板 + 学习模块（待办/计时/统计/分享卡）+ Joplin 的开放同步与数据自由，全部本地优先、开源免费。

5.3 设计原则

  • 3 秒可达：任何主界面到「开始记录」不超过 1 次点击（桌面快捷方式直达编辑器）；
  • 浅色温暖质感：米白纸张背景 + 低饱和青绿主色，圆角卡片，避免工具类 App 的冷硬感；
  • 无干扰写作：编辑器默认隐藏状态栏外一切元素；
  • 可访问性：正文不小于 14sp、触控目标不小于 44×44dp、支持系统字体缩放；
  • 先纸原型后 UI：用纸笔 / Figma 画完 5 个主页面线框并自己走查 3 遍再写代码。

06技术选型方案

6.1 客户端路线对比与决策

结合调研数据、独立开发人力与「Android 优先、未来上桌面/iOS」的目标，对四条候选路线打分（5 分制，为基于公开资料的工程评估，非统计数据）：

维度Flutter（推荐）React NativeKotlin + Compose 原生微信小程序
跨平台覆盖5（移动+桌面+Web）4.5（移动为主）2（Android 最佳，其余弱）2（仅限微信生态）
性能/流畅度4.5（自绘引擎）3（桥接开销）52.5
图文/多媒体 UI 效率53.543.5
同类开源项目验证5（Immich/AppFlowy/Moodiary）3.5（Joplin）31（无同类重应用）
本地能力（DB/文件/加密）4.5452（存储与相册受限）
你的学习成本3.5（新学 Dart，但语法简单）3（需 JS/React）4（有 Java/Android 基础）4.5（已学过）
综合结论首选次选保守备选不适合
决策：Flutter 3.x + Dart 3。理由：① 同类最成功项目全部采用，可直接读源码学习；② 一套代码覆盖 Android 手机和 Windows 桌面（你日常调试零成本）；③ Dart 语法接近 Java/JS，对有编程基础者约 1 周可上手；④ 图文密集 UI 正是 Flutter 最强项。
保守备选：若你希望完全复用已学的 Android 知识、且确定只做 Android，可用 Kotlin + Jetpack Compose + Room 实现等价架构，路线图不变。

6.3 本地存储策略（关键设计）

  • 结构化数据 → SQLite（Drift）：文本、标签、时间、路径等元数据入库，支持事务、迁移与 FTS5；
  • 媒体文件 → 文件系统：原图存 app_docs/media/yyyy/mm/uuid.jpg，同步生成 thumb/（长边 400px，质量 80）与 medium/（长边 1600px）两级压缩图，数据库只存相对路径；
  • 写入流程：编辑器先写临时草稿 → 防抖 500ms 事务入库 → 图片转码走 Isolate 后台线程，避免 UI 卡顿；
  • 容量控制：设置中提供「仅保留压缩图」开关；单条记录删除后媒体进入回收站，30 天清理；
  • 备份包：导出为单个 .mlbk（zip：db + media + manifest.json 版本清单），可整体恢复。

6.4 同步方案演进（不要一上来做复杂）

阶段方案说明
V1（MVP）手动/定时本地备份包零冲突风险，先保证数据不丢
V2WebDAV 单向备份（上传/恢复）对接坚果云免费额度即可验证链路
V3WebDAV 双向同步：每条数据带 uuid + updated_at + version + deleted 软删除标记，「最后写入获胜（LWW）」合并单用户多设备足够，避免 CRDT 复杂度
V4（可选）同步前 AES-GCM 端到端加密，服务端只存密文对齐 Joplin 隐私模型
多端同时编辑的冲突处理是本项目最难的工程点。第一版只做「备份/恢复」，双向同步放到第 13 周以后，且先用 LWW，绝不提前引入 CRDT。

07系统架构与数据模型

7.1 分层架构

采用轻量 Clean Architecture：表现层只依赖 Provider，业务逻辑在 Repository 之后，数据源可在「本地 Drift / WebDAV 远端」之间替换而不动 UI。（配套的分层架构示意图见对话中的独立可视化。）

  1. Presentation（表现层）：Page + Widget + Riverpod Notifier/Provider，负责渲染与交互；
  2. Domain（领域层）：实体模型（Entry / Asset / Notebook…）、仓库抽象接口、用例；
  3. Data（数据层）：Repository 实现 + Drift DAO + 文件存储 + WebDAV 数据源，负责模型与表结构映射；
  4. Core（基础服务）：数据库单例、图片管线、加密、备份、通知、权限等横切能力。

7.2 核心数据表设计（Drift / SQLite）

-- 笔记本（生活/学习空间与自定义本）
notebooks(id, uuid, name, space,            -- space: life | study | custom
          cover_color, sort_index, created_at, updated_at, deleted)

-- 记录主表（统一承载日记/笔记/速记/待办）
entries(id, uuid, notebook_id, type,        -- type: note|diary|quick|todo
        title, content_delta,               -- flutter_quill Delta JSON
        mood, weather_json, location_json,
        status, pinned,                     -- status: draft|normal|archived
        entry_date, created_at, updated_at, version, deleted)

-- 媒体资产（图片/音频，文件存文件系统）
assets(id, uuid, entry_id, kind,            -- kind: image|audio
        rel_path, thumb_path, medium_path,
        width, height, size_bytes, duration_ms,
        exif_json, hash_sha1, sort_index)

tags(id, uuid, name, color, created_at)
entry_tags(entry_id, tag_id)                -- 多对多

-- 学习模块
todos(id, uuid, entry_id, content, done, due_date, priority, updated_at)
study_sessions(id, uuid, subject, started_at, ended_at, duration_sec, note)

-- 全文检索虚拟表（FTS5，内容镜像 entries）
entries_fts(entry_id UNINDEXED, title, content_text)

-- 同步元数据 / 设置
sync_meta(key, value)
settings_kv(key, value)
所有需要同步的业务表统一带 uuid / created_at / updated_at / version / deleted 五个字段 —— 这是 V3 双向同步能够后补上去而不重构的前提，第一版建表时就要留好。

7.3 关键数据流：发布一条图文记录

编辑器页
  ├─ 选图/拍照 → 图片管线(Isolate)：转码 → 生成 thumb/medium → 写入私有目录
  ├─ 500ms 防抖 → EntryNotifier 校验
  └─ EntryRepository.saveEntry()
        ├─ Drift 事务：写 entries + assets + entry_tags + 更新 entries_fts
        ├─ 标记「待同步」队列 sync_queue
        └─ 返回 Stream → 时间轴/相册/统计页响应式自动刷新
（同步开关开启时）SyncWorker 消费队列 → 打包 → 可选加密 → WebDAV PUT

09质量保障与工程规范

测试策略

  • 单元测试：Repository、同步合并（LWW）、图片管线、统计计算，核心逻辑覆盖率目标 70%；
  • Widget 测试：编辑器自动保存、时间轴渲染；
  • 集成测试：「建记录→搜得到→备份→恢复」主链路；
  • 手工真机清单：权限拒绝、断网、低存储、进程被杀、暗黑模式、字体放大。

Git 与协作规范（单人也按团队标准）

  • 分支：main（可发布）/ dev（集成）/ feat/xxx（功能）；
  • 提交信息 Conventional Commits：feat: / fix: / refactor: / docs:；
  • 每个功能对应一个 GitHub Issue，PR 描述关联 Issue；
  • 每个里程碑打 tag，Release 写变更日志（CHANGELOG）。

数据安全红线

  • 任何写库操作走事务；删除一律软删除 + 回收站，不直接物理删除；
  • 每次版本数据库结构变更必须写 Drift Migration，禁止开发期「卸载重装」式偷懒；
  • 升级前自动生成本地备份；备份恢复流程在每个里程碑手动验证一次；
  • 权限最小化：定位、相机、相册权限按需申请并解释用途，不提前索权。
