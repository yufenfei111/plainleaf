## 一、报的问题与根因

> 「详情页附件区列表标题显示的是文件名，点开后实际文件名却是一串英文或乱码。」

**根因**：盘上落的是 `media/yyyy/mm/<uuid>.pdf`，而列表标题显示的是
`assets.original_name`（「作业第三章.pdf」）。此前把**盘上路径**直接交给系统应用，
于是系统标题栏、"另存为"的默认名、分享出去的文件名全是那串 uuid。

`AssetThumb` 的注释里其实已经写明这条设计（"用户看到一串 uuid 毫无意义"），
但当时只解决了**列表里显示什么**，没解决**交出去的文件叫什么** ——
"显示名"与"物理文件名"是两个概念，只在列表里做对了不算修完。

**关键判断：库内用 uuid 是对的，不该去动存储层。**
按原名存盘会立刻带来三件必须处理的事：同名冲突、非法字符（`/`、`:`、`?` 在 Windows
上写不进去）、以及"文件名可控"带来的路径穿越风险。问题只出在**交出去这一步**，
所以修在交出处。

## 二、方案：`AttachmentHandoff`（新增）

`lib/core/media/attachment_handoff.dart`：

```
prepare(sourceAbsPath, displayName)
  → 展示名不可用 / 已与盘上文件名一致  → 直接返回原路径（**不复制**）
  → 否则复制到 {临时目录}/plainleaf-handoff/{库内文件名}/{展示名}
```

### 三个设计点

| 点 | 为什么 |
|---|---|
| 副本放在**以库内文件名命名的子目录**里 | 两个不同记录挂同名文件时不会互相顶掉；同时**文件名本身仍是干净的展示名**。给"另存为"默认名加 uuid 前缀是最省事的做法，而那恰恰是要修的毛病 |
| 放**系统临时目录**，进程内首次使用时清理 7 天前的旧副本 | 临时目录可被系统回收；清理只是"别越攒越多"，失败就静默跳过，不影响打开 |
| 盘上文件名已等于展示名时**不复制** | 历史数据没有 `originalName`，展示名回退成文件名本身 —— 那种情况下平白多占一份空间 |

### 展示名清理规则（`safeDisplayFileName`，纯函数）

- 取 basename **之后再把残留分隔符也替掉**：`p.basename('/')` 在各平台上下文里
  并不都返回空串（可能原样返回 `/`），只靠 basename 会漏出一个名叫 `/` 的文件；
- 替换 `<>:"|?*/\` 与控制字符（Windows 上直接写不进去）；
- 去掉结尾的 `.` 与空格（Windows 会静默丢弃，导致"我明明叫这个名字"对不上）；
- 按 **UTF-8 字节数**截断并保留扩展名 —— 不能按字符数截：ext4/NTFS 单段上限
  都是 255，而中文一个字占 3 字节，按 120 字符截在中文长标题上照样超限，
  届时得到的是"文件名过长"的写盘失败，比截断更难排查。

### 影响的调用点（4 处）

| 位置 | 说明 |
|---|---|
| 详情页附件区「打开」 | 使用者报的那个入口 |
| 编辑器附件条「打开」 | 同一个洞，只是没人报 |
| 相册查看器「保存到设备」 | 桌面端此前用 `basename(sourcePath)` = uuid。为此给 `GalleryAsset` 补 `originalName`，并把它接到 `ImageSaver.save(asName:)` |
| 平台相册的保存 | `gal` **不支持自定义文件名**，刻意忽略 `asName` 并在注释里写明这是平台限制 |

> 「打开」与「保存」共用同一个 `safeDisplayFileName`。两条链路各写一份清理逻辑的结局，
> 必然是同一个附件有两个名字。

## 三、P1-9 · 音频封面与时长

### 依赖选型（本阶段唯一能"本机验完再交付"的 P1 项）

`audio_metadata_reader ^1.8.0` —— **纯 Dart**，自己解析 ID3v2 / MP4 ilst /
Vorbis Comments，不走平台通道。与 `file_selector` / `open_filex` / `gal` 不同，
它**不需要真机验证**。

> 这条对比是本轮做优先级排序的主要依据：本项目每引入一个平台插件都要付出
> 真机验证的代价，AGP 9 与 win32 的冲突已经堵死过 `file_picker`（三轮）。

### 实现

- `lib/core/media/audio_metadata_probe.dart`：读时长 + 内嵌封面，跑在 `Isolate`
  （与 `ThumbnailPipeline` 同一口径：解码不在主线程抢 16ms 帧预算）；
- 封面**先落临时文件**再交给现有的两级缩略图管线 —— 复用同一套尺寸/质量控制，
  比另写一套缩放可靠。封面尺寸可能 1500×1500，直接当 thumb 存会破坏 thumb 契约；
- 挑封面时**正封面优先**：一首歌可能同时带正封面/封底/艺术家照片，
  取第一张会在某些 tag 上拿到封底或 Logo —— "缩略图是张不明图片"比没有封面更难理解；
- `assets.durationMs` 字段 W4 建表时就预留了，`AssetsDao.updateDuration` 回填。

### 两个刻意的决定

| 决定 | 理由 |
|---|---|
| `_derive(writeSourceMeta: false)` | 封面只是封面，不是资产本身。把封面的字节数写成音频文件的 `sizeBytes`，会让详情页的"文件大小"凭空小掉两个数量级；把 300×300 写进 `width/height` 同样是错的语义。已用例钉住 |
| 读不出元信息一律降级 | `aac` / `wma` / `amr` 不在该库支持的容器里，残缺文件也会抛。**契约是"任何文件都能记进来"** —— 时长与封面只是加分项，不能让挂接失败 |

### 展示

详情页附件行从「原名 + 大小」变成「原名 + **时长 · 大小**」（`3:45 · 4.2 MB`）。
时长排在前面：音视频里它才是用户确认"是不是这一条"的信息。
有封面的音频由 `AssetThumb.forAsset` 自动渲染缩略图 —— **组件层无需改动**，
这正是 W19 收口带来的收益。

## 四、P1-10 · 按附件类型筛选

### 语义：**含**该类附件，不是"只带该类"

一条同时挂图和 PDF 的记录，在「PDF」条件下**应当出现** —— 用户找的是
"哪条记录里有 PDF"。已用四个条目（只有 PDF / 只有图片 / 两者都有 / 没附件）
的用例把这条语义钉住。

### 必须下推 SQL

`EntriesDao._hasAssetOfKind` 生成子查询条件（`entries.id.isInQuery(...)`），
在 `watchTimeline` 与 `selectIdsByFilter` 两个入口都生效。

**用例专门验证这一点**：三条记录按日期倒序，带 PDF 的是最早那条；
`limit: 2` 时若在客户端过滤，结果会是空列表 —— 而这正是 W7 定下
"筛选一律下推 where"那条红线的由来。已软删的附件不计入命中。

### UI

筛选弹层新增第四段「附件类型」（不限 / 图片 / PDF / 文档 / 视频 / 音频 / 压缩包）。
刻意**不含 `other`**：它的 label 是「文件」，一个叫"文件"的条件等于"有附件"，
而"有附件"这个意图用不上筛选。

`TimelineFilter` 的 `==` / `hashCode` / `activeCount` / `copyWith` 同步带上新维度 ——
漏掉 `==` 会让"筛选一变就清空已选"（W15）静默失灵。

## 七、P1-8（PDF 首页缩略图）为什么本轮没做

**不是遗忘，是刻意推迟**，理由如下：

| 事项 | 具体风险 |
|---|---|
| 依赖形态 | `pdfx` 是平台插件：Android 走原生 `PdfRenderer`，**Windows 需要 PDFium**，且要用 `dart run pdfx:install_windows` 改 `windows/runner/CMakeLists.txt` |
| AGP 9 兼容性 | **未知**。`file_picker` 就是在 AGP 9 下"依赖能解析、编译期找不到符号"，三轮才查清 |
| 验证手段 | 本机 `flutter test` 覆盖不到平台通道；Android 侧必须真机。**改完无法证明它能用** |
| 代价对比 | 上面每一条都是"可能白做"，而 P1-9/P1-10 是"本机验完即交付" |

**建议**：等 `pdfx` 的 AGP 9 兼容性被确认（或换一个纯 Dart 方案）后再排，
并且与真机走查打包成一轮 —— 那批工作本来就要连真机。
